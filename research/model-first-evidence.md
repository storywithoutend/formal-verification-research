# Model-first software development: evidence and guarantee taxonomy

Validated 2026-11-19. This report supports the experiment in
[`research/model-first-brief.md`](./model-first-brief.md).

## Reading the guarantees

A green result below applies to the formal artifact and assumptions named in that
row. It does **not** automatically prove that a deployed TypeScript program, its
runtime, its dependencies, or its environment are correct.

| Guarantee class | What is established | What is not established |
|---|---|---|
| **Full proof** | A proof checker accepts a proof that a formal program/model satisfies a formal statement for all values represented by the definitions. The result is relative to axioms and the trusted computing base. | That the statement captures the intended requirement; that hand-written translations, compilers, runtimes, foreign functions, or deployment environments preserve it. |
| **Refinement proof** | A lower-level formal model simulates or implements an abstract formal model, preserving the stated observations/properties under the refinement mapping. | Correctness of an unmodelled executable, environment, or mapping to production events. |
| **Bounded exhaustive model checking** | Every reachable state in the configured finite model (TLC), or every behavior up to configured symbolic bounds (for bounded Apalache checks), satisfies the checked property. | Behavior outside the chosen constants, bounds, abstractions, fairness assumptions, and model. It is not a proof of the implementation. |
| **Trace validation** | One observed implementation trace, after a declared event/state mapping, is admitted by the specification. Repeating it checks more observed traces. | Unobserved executions; omitted variables/events; correctness of instrumentation; completeness of the abstraction; all future behavior. |
| **Model-based testing** | Generated command/event sequences keep an executable and a test model in agreement for the executed samples and assertions. | Exhaustive behavior unless the generated finite graph is explicitly and completely traversed; correctness outside the test adapter and oracle. |
| **Empirical tests** | Selected examples, properties, fuzz cases, or mutants behaved as expected in the tested environment. | Universal correctness. A high mutation score measures the test suite against the selected mutation operators, not against all possible faults. |

## Findings for a TypeScript / Effect model-first workflow

1. **The strongest practical near-term chain is layered, not singular.** TLC can
   exhaust a finite concurrency model; deterministic Effect services can replay
   schedules; trace validation checks observed executions; fast-check explores
   command sequences; Stryker measures test sensitivity. These guarantees compose
   as evidence, but they do not collapse into a proof of the deployed program.
2. **Trace design is the key bridge.** Both trace-validation papers require an
   explicit mapping from concrete events to abstract actions/state updates. The
   mapping, event completeness, and atomicity grain are trusted engineering work.
3. **Generated verified IR is credible for pure cores, less mature for TS
   workflows.** Dafny, Verus, Lean, SynVer, and VeriGen-C show that agents can use
   verifier feedback. None supplies a verified TypeScript/Effect backend or a
   proof-preserving treatment of the Node event loop, npm dependencies, RPCs, and
   browser behavior.
4. **Specification error remains the dominant common-mode risk.** The ICML spec
   paper evaluates specs through trusted cases rather than claiming semantic
   equivalence; VeriGen-C explicitly warns about weak verified contracts; all
   proof/model tools accept a faithfully checked but wrong statement.
5. **Visual tools differ in authority.** An XState, Alloy, UPPAAL, or Event-B model
   can be executable/analyzable input. A state visualization or counterexample
   diagram is only a view of that input/result. Version-control the textual or
   serialized model and regenerate views.

## Bibliographic discrepancies and unverified items

- The SEFM conference occurred in 2024. Crossref records the chapter publication
  in 2024, while some Springer search displays label it 2025; this report uses
  the conference/proceedings year and records the discrepancy.
- SynVer’s arXiv v1 has an earlier title and author list. The evidence row uses
  the published ASE metadata and DOI.
- The Dafny-IR work is a workshop paper/arXiv preprint with no DOI found.
- VeriGen-C is an arXiv preprint with no peer-reviewed venue or artifact found.
- Dedicated archival artifacts for the SEFM trace-validation and Coins papers
  were not found from their primary publication pages and are marked
  **UNVERIFIED**, rather than inferred.
